# Step4：结果交回

向调用方返回本批逐 API 结果及任务结果目录中的 `api-loop/result.json` 路径，包含适配策略、前序确定的类别、分流结论、测试文件、实际验证结果及后续步骤。

分别统计输入 API 数、策略为 `补充testcase` 的 API 数及成功生成用例的 API 数。实际运行后统计真实通过、失败及未完成项，不能用生成数量代替执行通过数量。

本批适配和复测结束后，子 agent 按最初分配的 API 清单逐项核对 `api-loop/result.json` 及最终报告。该 API 的规定用例全部通过且验证充分，列入交付清单，并核对 `adapt-information.json` 中 `api-status["<数据库正名>"]` 为 `支持`。最终仍有任一规定用例失败，整项撤回该 API；直接用例和交叉用例执行同一规则。最终缺少必要验证的 API 也整项撤回，原因记为验证不足。向主控交回保留清单，并报告“计划 N 个、完成 M 个、撤回 K 个”，核对 N = M + K。

对最终确认不支持或验证不足而撤回的 API，清除它在本批任务中留下的全部记录和改动，包括 run-data 中的任务清单、计划、状态、测试结果和报告，本批 branch-mapping 中的对应项，开发分支中涉及该 API 的改动和测试，以及 issue、PR 材料里的表述和统计。共享文件只清除该 API 对应的部分。保留 `api-classification` 和 SQL 表中的数据。先预览本批范围，再执行同一命令去掉 `--dry-run`：

```bash
python3 "$SKILL_DIR/scripts/withdraw_api.py" --run-dir "$RUN" --api "$API" --dry-run
```

脚本按数据库正名清理本批任务、分支占用和活动结果。只自动删除能确认归属和内容的专属测试、交接和证据。先核对预览列出的源码、共享实现和交叉用例；共享文件中需修改的部分由子 agent 按保留项逐处处理，并复测受影响的用例。依据剩余任务重写 issue/PR 草稿、重算统计。原始混合报告沿用原件，从保留项的明细汇总。混合复测请求失效时，按返回的保留项另建请求。

执行中断时对同一 API 重新执行。本批任务文件中的 `withdrawn-apis` 用于准备阶段跳过已撤正名。已有 PR 时，由主控通过原发布流程更新远端和收据；全部撤回时结束发布并单独处理原开放 PR。

当前其余三类为待评估，不称为已生成、已验证或不需要。后续产生逐类评估时，一并交回结论、依据及尚缺的生成能力。

适配项交回 Step2 设计、修改前证据、Step3 实际修改文件与符号、修复后实测报告及验收结论。仍在实施、修复或等待复测时，标明恢复步骤，待取得最终结果后再计入本批交付统计。其他专项策略、生成失败或信息缺失分别说明原因。

根据本批结果提供 issue 和 PR 所需的问题描述、改动说明及验证材料；已有 issue/PR 信息从交接材料复用。由调用方统一提交 issue、commit、push 和上传 PR，本 skill 不独立发布。没有适配实现改动时如实说明仅补充了测试，不虚构实现缺陷。

本步完成表示当前材料已交回；整个任务是否完成，由调用方根据未完成项及实际发布结果判断。
