# Step0：查表分流

读取本次 API 清单及交接的信息来源，沿用提供的源码、环境和实际开发分支；相对路径按调用方明确的根目录解析。

按输入顺序处理 API 清单。名称沿用输入，不批量补 `torch.` 或自行改名；生成器需要完整名称时，根据本次源码定位对应入口，不能明确定位的项记录为未完成。

## 查询适配策略

先读取本次`adapt-information.json.api-status`。已记录的`待适配`或`支持`用于本批续跑，避免再次按数据库中的旧`补充testcase`重新生成；没有本批状态时才按数据库策略分流。API可用性和正名仍以当前数据库核对。

只读查询调用方提供的 API 策略表，按 API 名称匹配；`API真正名字`非空时，读取正名行的适配策略。原名称或正名为对内入口、标记为`API删除，待下线`时，不进入用例生成；`文档删除，待下线`不作为接口不可用的依据。数据源、表名、列名及路径基准以交接说明为准，不从 skill 安装位置推导。不要重新生成数据库或修改表中策略。

| 查表结果 | 本轮处理 | 后续步骤 |
|---|---|---|
| `适配策略=补充testcase` | 进入 Step0.1，默认先生成功能类用例 | 待 Step1 运行功能测试后，再评估其余三类 |
| `待适配` | 携带已有用例和失败材料，交Step2 | 当前直接结束，交回待适配状态 |
| `支持`或数据库策略`已支持` | 结束该API的生成和开发，交回已有结论 | Step4汇总材料；已有结论不能冒充新的执行记录 |
| 其他非空适配策略 | 说明当前专项策略及未完成事项 | 按对应组件处理，当前不猜测专项实现 |
| 数据库或 API 条目缺失、策略为空、名称无法匹配 | 记录具体缺项并结束该项 | 先补齐信息，不猜测策略 |

首次按数据库的`待适配`分流时，在结果文件中记录该项，并用`record_api_status.py`同步到本次`api-status`，调用方式沿用[Step1的状态记录入口](step1-testcase_validation.md#写入adapt-information并分流)。没有实际执行时保持`execution=not_run`，再交Step2结束。

名称优先精确匹配；`Tensor` 与 `torch.Tensor` 及对应成员可按已规定的等价名称匹配，不扩展到其他模糊匹配。这里直接按适配策略分流，不用“本地是否适配”代替策略查询，也不把其他策略判定为已经支持或无需后续处理。

批量任务逐 API 判断；只统计策略为 `补充testcase` 的不同 API 数为本批补测数，不等于输入 API 总数或测试方法数。空任务不调用生成器。

在任务结果目录的 `api-loop/result.json` 保存策略、分流结论和后续步骤，格式见[结果记录约定](../references/API-Testcase-relationship.md)。新补测项按本次已明确的缺口生成；已有生成文件和有效记录直接续用。其他项覆盖状态保留`unknown`，不从策略名称推断用例已覆盖。执行状态均从 `not_run` 开始。

补测项默认 `test_type=functional`；内存、精度、确定性先记录为 `pending_evaluation`。当前表只给出 `补充testcase` 总策略，没有四类测试的独立结论，不从该策略直接推断四类都需要生成。

同一批重跑时保留已生成文件和有效记录，不无条件重置或覆盖已有用例；旧执行结果不能冒充本次运行结果。
