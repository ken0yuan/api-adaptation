# Step0：查表分流

## 输入

沿用 [SKILL.md](../SKILL.md#输入) 中调用方提供的信息，本步使用以下输入。

| 输入 | 读取内容或用途 |
|---|---|
| 待处理 API 清单 | 本次查询的 API 名称及原顺序，如有上游任务标识则保留 |
| API 策略数据库路径及表名 | 使用调用方交接的数据库和表名 |
| 任务状态文件`adapt-information.json` | 读取 `api-status`，按 API 正名取得本批已有进度 |
| 结果目录 | 保存本次 `api-loop/result.json` |
| 已有 `api-loop/result.json` | 同批续跑时保留已有用例记录和有效测试结果 |

### 策略表字段

| 字段 | 用途 |
|---|---|
| `API名称` | 匹配输入名称或正名 |
| `API真正名字` | 定位别名对应的正名行 |
| `是否对外` | 核对原名称及正名是否为对外入口 |
| `是否支持` | 核对原名称及正名是否已从 wheel 下线 |
| `适配策略` | 确定该 API 的处理步骤 |
| `API适配分类` | 保留数据库分类，供 Step0.1 准备用例生成交接 |

## 查询适配策略

按输入顺序处理 API 清单，名称及任务标识沿用输入。

### 1. 读取本批进度

先读取任务状态文件的 `api-status`。已记录的`待适配`或`支持`用于本批续跑，避免异常中断后再次按数据库中的旧`补充testcase`重新生成；没有本批状态时才按数据库策略分流。API可用性和正名仍以当前数据库核对。

若已有结果中该 API 的 `next_step=step0.1`，优先继续尚未完成的生成或修复任务，沿用 `notes` 中的问题和原 API 身份。

### 2. 核对数据库条目

只读查询本次交接的策略表。原名和正名均在同表匹配；表或条目缺失时报告具体缺项。

AI_LOOP 可在本步直接运行以下命令，读取同表正名、适配策略和分类，按下方规则分流。后续步骤沿用返回的 `classification_source`。

```bash
python3 <api-adaptation安装目录>/scripts/prepare_testcase_handoff.py --strategy-only \
  --database <API策略数据库绝对路径> --run-dir <本次运行目录> --api <本次API名称>
```

独立调用时用 `--table "<调用方表名>"` 代替 `--run-dir`。

1. 匹配 API 名称。
   - 优先精确匹配。
   - `Tensor` 与 `torch.Tensor` 及对应成员可按已规定的等价名称匹配，不扩展到其他模糊匹配。
2. 定位正名。
   - `API真正名字`非空时，读取正名行的适配策略和分类。
3. 核对原名称和正名的可用性。
   - 为对内入口或标记为`API删除，待下线`时，不进入用例生成。
   - `文档删除，待下线`不作为接口不可用的依据。

### 3. 确定后续步骤

逐 API 记录分流结果，查完本批清单并保存结果后，再交付下一步。

| 适配策略或本批状态 | 本步记录 | 后续步骤 |
|---|---|---|
| `适配策略=补充testcase` | 新补测项记为 `next_step=step0.1`，续跑项保留已有进度 | Step0.1，已有生成结果时按记录续跑 |
| `待适配` | 记录待适配项，`next_step=step2`，保留已有材料 | Step2 |
| `支持`或数据库策略`已支持` | 保留已有结论，`next_step=step4` | Step4 |
| 其他非空适配策略 | 说明当前专项策略及未完成事项 | 按对应组件处理，当前不猜测专项实现 |
| 数据库或 API 条目缺失、策略为空、名称无法匹配 | 记录具体缺项并结束该项 | 先补齐信息，不猜测策略 |

- 按适配策略逐 API 分流，不用“本地是否适配”代替策略查询，也不把其他策略判定为已经支持或无需后续处理。
- 本批补测数只统计策略为 `补充testcase` 的不同 API 数，不等于输入 API 总数或测试方法数。
- 空任务不调用生成器。

### 4. 保存本批结果

在结果目录的 `api-loop/result.json` 保存策略、分流结论和后续步骤，字段含义见 [result.json 字段说明](../references/API-Testcase-relationship.md)。

1. 记录执行状态。
   - 首次查到 `待适配` 时，记录 `strategy=待适配`、`execution=not_run`、`next_step=step2`。
   - 新建记录的执行状态从 `not_run` 开始。
2. 初始化测试类型。
   - 补测项默认 `test_type=functional`。
   - 内存、精度、确定性先记录为 `pending_evaluation`。当前表的 `补充testcase` 总策略不能直接判定四类测试都需要生成。
3. 保留同批已有成果。
   - 续用已生成文件和有效记录，不无条件重置或覆盖已有用例。
   - 旧执行结果不能冒充本次运行结果。
4. 安排状态同步。
   - 本批有补测项时，由 Step1 统一同步任务状态。
   - 本批没有补测项时，使用 `scripts/record_api_status.py` 同步已确定的状态。命令见 [Step1 的状态记录入口](step1-testcase_validation.md#汇总结果并更新状态)，`--adapt-information` 传入本次任务状态文件的实际路径。

### 5. 交付下一步

结果保存后，按本批分流情况继续。

1. 有需要生成或补充用例的 API 时，读取并执行 [Step0.1：生成功能用例并完成 NPU 验证](step0.1-testcase_development.md)。
   - 传入本批补测 API 清单、原任务标识和已保存的 `api-loop/result.json` 路径。
   - 沿用调用方提供的数据库、源码、环境、开发分支、任务范围和结果目录，按本次已明确的缺口生成用例。
   - Step0.1 交付后，执行 [Step1：接收 NPU 结果，运行 GPU 并记录状态](step1-testcase_validation.md)。
   - 已有生成结果且无需补充用例的 API，按已有进度进入 Step1。
2. 待适配项等本批 Step0.1 和 Step1 完成后，与测试失败后新增的待适配项一起交 [Step2：待适配入口](step2-scheme_design.md)。本批没有补测项时，直接交回待适配项。
3. 已支持项由 [Step4：结果交回](step4-result_handoff.md) 汇总已有结论和材料。已有结论不能冒充新的执行记录。
