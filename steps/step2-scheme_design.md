# Step2：从失败用例确定修改点

从本批 `api-loop/result.json` 取 Step0 直接分流的待适配项和 Step1 已定位为适配问题的失败项。沿用原 `task`、`api`、`database_api`、策略表、源码及开发分支。承接 Step1 按功能列出的缺口和候选方案，逐项核实并写出最终改法与验收用例；当前平台缺能力的，记录依赖方、缺少的接口及何时可以验证。

## 取本次失败用例

- **Step1 已测出缺口**：从该项的 `test_files`、`report` 和 `device_validation.npu` 找到原用例标识、失败调用（含重载、输入、设备）、预期和实际报错或断言。如果与本次源码、构建及场景一致，直接引用这次运行作为修复前基线，开始查实现。GPU 对照已有时复用。仅当基线版本不同、失败现象不清或证据缺失时，针对有疑问的那一例补测。
- **Step0 直接转入**：先看随任务交来的失败记录；可对应同一版本和调用时同样复用。只有策略表的“待适配”标记时，优先运行固定版本上游对应的现成用例；没有合适用例才写最小复现。保存命令、用例标识、预期、实测和日志。环境问题或不符合上游契约的断言分别交回环境处理或用例修复。

## 从原断言找到实现偏差

先把失败写成一句可验证的话：**哪个版本、哪个公开调用，在什么输入下应当得到什么，NPU 实际得到了什么。** 用目标版本的上游源码、schema 或现成用例说明预期。区分调用应产生的变化和应保持的属性。例如，布局转换既要改变 stride，也要保留 shape 和数值。沿原报告记录测试解释器、实际加载的构建及其对应源码，区分开发分支和失败 wheel 的版本。

**定位问题时参考昇腾历史适配。** 有相似的修改记录或[适配案例](../examples/operator-adaptations.md)时，看当时怎样缩小问题范围、用什么检查区分可能的原因，以及修复时遇到了哪些昇腾后端特有的限制。没有相似案例时，沿本次失败调用查源码并验证。

沿该调用实际经过的符号向下追。根据尚待区分的原因选择检查，已有记录能说明的直接引用。

| 待区分的问题 | 用什么证据决定修改点 |
|---|---|
| 公开入口传错了参数，还是下层实现有误？ | 用同一组有效输入检查包装层传给下层的实参、默认值和返回结构，再直接调用下层。如果下层满足契约，修包装层中发生偏差的转换。 |
| 具体重载缺注册，还是已有实现的语义不够？ | 读运行时的准确 schema、分派表和原失败记录。区分直接 kernel、组合实现和 fallback。与正常相邻重载比对 dtype、别名、写回及返回约定。现成 kernel 能覆盖目标重载时，沿相邻条目补维护中的注册声明或模板。 |
| 组合调用中，哪个原语引入了偏差？ | 用独立输入观察各原语。若上一步已产生错误，把满足前置条件的输入单独交给下游，再看下游是否仍破坏结果。例如公开调用依次执行 clone 和 resize 时，这个检查决定修复该公开调用是否还需改 resize。 |
| 偏差只发生在设备实现、编译或多 rank 路径？ | 保留原失败模式。沿实际调用进入 op-plugin、aclnn、图编译或 HCCL 的对应符号，用相邻正常实现作对照。复用候选接口前，核对本次调用所需的输入、输出和副作用。 |

用本次实际观测解释“这个符号怎样导致原断言失败”。仍有两个解释会导向不同改法时，记录哪一项检查能区分它们。

## 写出可实施的改法

**设计新功能时参考 CUDA 实现。** 优先从目标版本的 PyTorch 源码追踪同一公开 API 在 CUDA 上实际执行的代码。看它怎样完成这个功能，哪些逻辑属于共享层，哪些操作由设备后端提供。把参考提交、文件、符号和应保持的行为写进方案，再对照 NPU 已有接口决定具体改法。CUDA 走共享 Python 或组合实现时，引用实际共享路径即可。见[按入口查 CUDA 实现](../references/cuda-and-compatibility.md#从公开入口找到-cuda-实现)。

在本次运行目录保存一份短方案，例如 `api-loop/design/torch.add/v1.md`。让接手者能从原用例一路查到改动及其验收依据：

- **失败与根因**。引用原用例、报告和上游依据，给出实际调用链、首个偏差符号，以及选定该修改层的观测结果。
- **具体改法**。写出目标仓库、维护中的文件与符号，说明当前行为、拟修改的逻辑，以及可复用的相邻实现。对每一处拟改动说明它解决了原调用的哪个问题。
- **验收**。把每处改动对应到可执行用例或命令，写明原失败断言修复后的预期。涉及共享实现时，点出受影响的相邻调用及应保持的行为。涉及跨仓接口、精度或性能时，再列依赖版本、适用边界、验收阈值及回退方法。

证据不足时，在当前项 `notes` 中记录缺口和复现位置，保留 `待适配 / step2`。用例自身有误的补测项走 Step1 原有修复入口。依赖 CANN 新能力时记录缺少的接口、版本和联合验证条件，交调用方跟进。若基线已满足契约，交回 Step1 用实际验证材料核对支持结论，避免为已支持行为制造实现改动。

## 交给 Step3

核对根因、修改范围和验收条件，按本批已有评审约定记录结论。已具备实施条件且任务范围包含开发时执行下列命令。只要求方案的任务交回设计及证据。

```bash
python3 "$SKILL_DIR/scripts/npu_handoff.py" design \
  --results "$RUN/api-loop/result.json" --api "$API" --design "$DESIGN"
```

`API` 取原 `results[].api`，`DESIGN` 为本次运行目录内的设计文件。命令归档该项的原始结果、绑定方案 SHA256，并把当前验证置为 `not_run`。重复交接同一文件复用原记录。方案有变时另存新版，保留旧文件与尝试。随后进入 [Step3](step3-code_development.md)。
