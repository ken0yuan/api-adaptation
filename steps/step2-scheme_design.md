# Step2：从失败用例确定修改点

从本批 `api-loop/result.json` 取 Step0 直接分流的待适配项和 Step1 已定位为适配问题的失败项。沿用原 `task`、`api`、`database_api`、策略表、源码及开发分支。已由 Step1 确认并交主控发布的平台限制沿用该交付路径。

## 取本次失败用例

- **Step1 已测出缺口**：从该项的 `test_files`、`report` 和 `device_validation.npu` 找到原用例标识、失败调用（含重载、输入、设备）、预期和实际报错或断言。如果与本次源码、构建及场景一致，直接引用这次运行作为修复前基线，开始查实现。GPU 对照已有时复用。仅当基线版本不同、失败现象不清或证据缺失时，针对有疑问的那一例补测。
- **Step0 直接转入**：先看随任务交来的失败记录；可对应同一版本和调用时同样复用。只有策略表的“待适配”标记时，优先运行固定版本上游对应的现成用例；没有合适用例才写最小复现。保存命令、用例标识、预期、实测和日志。环境问题或不符合上游契约的断言分别交回环境处理或用例修复。

## 确定改哪一层

ATen 注册、组合原语或张量元数据相关的失败，使用[实现定位手册](../references/api-implementation.md)里的分派探针和原语拆分方法。先根据现象选择一项能区分候选原因的检查，将观察结果和对应符号写入本 API 的方案。

1. 从失败调用取得目标版本的公开签名或 ATen schema，区分具体 overload、默认参数及 `out` / 原地形式。跟到 NPU 侧第一个与预期不同的符号。纯 Python API 直接追包装函数；有 ATen 分派的 API 查实际注册及后端实现。
2. 在同一 checkout 中找一个能工作的相邻重载或同类 API，对照注册声明、调用参数和返回值。可用 `git grep -n -F '<算子名或包装符号>'` 在目标仓搜索。按该版本实际布局查看 `torch_npu/csrc/aten/` 下的声明、`torchnpugen/` 的生成来源，或已检出的 `third_party/op-plugin/`。若注册由代码生成，定位到被维护的声明或模板。
3. 按证据选择修改点。已有 kernel 且覆盖目标语义、仅缺注册时，沿用相邻注册；参数、默认值或返回结构在包装层发生偏差时，修对应转换；已到达正确实现但设备结果仍错时，再追 op-plugin、aclnn 或实际所用后端。涉及 HCCL 或图编译时沿那条调用链核对。有现成实现可复用时，同时检查失败用例所需的 dtype、别名或异常语义。

在本次运行目录保存一份短方案，例如 `api-loop/design/torch.add/v1.md`。写清原用例和报告位置、上游预期、目标文件与符号、参考的相邻实现，以及修复后要跑的原断言和受影响的相邻用例。单一重载的注册缺口写到这个粒度即可。涉及跨仓接口或精度、性能变化时，再补充依赖版本、适用边界、验收阈值和回退方法。

证据不足时，在当前项 `notes` 中记录缺口和复现位置，保留 `待适配 / step2`。用例自身有误的补测项走 Step1 原有修复入口。依赖 CANN 新能力时记录缺少的接口、版本和联合验证条件，交调用方跟进。若基线已满足契约，交回 Step1 用实际验证材料核对支持结论，避免为已支持行为制造实现改动。

## 交给 Step3

核对根因、修改范围和验收条件，按本批已有评审约定记录结论。已具备实施条件且任务范围包含开发时执行下列命令。只要求方案的任务交回设计及证据。

```bash
python3 "$SKILL_DIR/scripts/npu_handoff.py" design \
  --results "$RUN/api-loop/result.json" --api "$API" --design "$DESIGN"
```

`API` 取原 `results[].api`，`DESIGN` 为本次运行目录内的设计文件。命令归档该项的原始结果、绑定方案 SHA256，并把当前验证置为 `not_run`。重复交接同一文件复用原记录。方案有变时另存新版，保留旧文件与尝试。随后进入 [Step3](step3-code_development.md)。
