# Step1：接收 NPU 结果，运行 GPU 并记录状态

接收 Step0.1 的用例和 NPU 环境中的验证材料。验收后，将同一版测试上传 GitHub，在 GPU 服务器执行并保存结果。

有效的 NPU `fail` 或 `blocked` 也继续 GPU 参考验证，两侧结果分别保存。

Step3 交回的实现回归使用同一快照核验和状态同步命令。读取该 API 的设计和修改后报告，核对原失败断言及设计中的必测项。用例缺口按本步流程退回 Step0.1；用例有效且测出实现错误时回 Step3，实施回归通过后进入 Step3.1。

## 接收 NPU 结果

1. 确认本次验证范围。
   - 默认接收 NPU 结果，再进行 GPU 验证。
   - 只要求 NPU 时，验收后按 NPU 执行结果[更新本批 API 状态](#汇总结果并更新状态)。
   - 只要求 GPU 时，从 GPU 入口开始，NPU 保持原记录。
   - 先准备不触发或指定其他参考设备时，按调用方要求执行。
2. 逐 API 核对快照、报告、日志及当前文件。

```bash
python3 <api-adaptation安装目录>/scripts/npu_handoff.py verify \
  --source <torch_npu源码仓> --results <本次api-loop/result.json> --api <results[].api>
```

### NPU 验收条件

#### 1. 仓库规范与用例审查

完整读取目标仓 README，记录来源提交和文件哈希。

```bash
git -C <torch_npu源码仓> rev-parse HEAD
sha256sum <torch_npu源码仓>/test/api_supplement/README.md
cat <torch_npu源码仓>/test/api_supplement/README.md
```

1. 将来源提交及哈希记入该 API 的 `notes`。
2. 对照 README 与生成器自检记录，核对目标仓要求。
   - 重点检查 API 方法命名。
   - 按 API 是否依赖硬件，核对设备选择和实际执行行为。
   - 对 GPU/NPU 共用的用例，检查设备分支和 helper。两侧可以用各自的设备、流及初始化方式；对照同一功能时，应保持等价输入和初始状态，核对目标调用次数、同步相对位置及断言使用的返回值或副作用。例如验证 CPU offload 首次返回值，就在两端断言第一次 `scale()` 的结果。若某端需要单独验证另一种保证，分开记录观察值和适用设备。
   - 发现目标仓要求与生成器模板冲突时，将具体差异交回生成器修复本次用例。
3. **这个 API 要测哪些用法？** 先读目标版本 PyTorch 源码里这个 API 自己的声明和 docstring。算子有 YAML 定义时，看对应重载的参数、默认值和返回值；Python 接口看函数或方法的签名。结合 docstring 里的参数说明和示例，列出哪些用法会改变结果或状态，再对照 Step0.1 的用例逐项检查。某个行为在声明和说明里没写清时，再查对应实现。
   - 对每项功能，写明 NPU 已有的实现入口。还缺的，列出可行的适配办法和验收用例，交 Step2 设计。涉及 CUDA 时先看它实际完成了什么，再找 NPU 上的对应做法。
4. **用例真的测到了吗？** 找到调用 API 的那一行，以及检查这次调用结果的断言，再从本轮 JUnit 或日志确认这个方法确实跑过。例如，用例要验证“等待另一个进程”，如果去掉等待，断言仍然会通过，就要退回 Step0.1 补用例。
5. **为什么能跳过？** 写明是哪条 skill 规定或目标版本的哪段 PyTorch 原文排除了这种用法，并解释它为什么适用于当前场景。说已有用例测过，就指出测试方法和断言。拿不出依据，或发现整项漏测，就写清要补哪次调用、检查什么结果，退回 Step0.1。有效用例因缺依赖没跑起来，补环境再测；有效用例跑出了 NPU 实现错误，首次交 Step2，已有方案的交 Step3。

按[功能审核记录](../references/API-Testcase-relationship.md#功能审核记录)保存本次判断并同步状态。需要补用例时，确认该 API 已回到 `next_step=step0.1`。

#### 2. 生成器自检记录

1. 核对生成器按主文档和对应类别规范完成的自检。
   - 在独立工具虚拟环境直接下载并运行生成器要求的仓库 flake8 及插件，检查时使用目标仓配置。运行时 `requirements.txt` 和共用测试 venv 只用于执行用例。
   - 复用已交付的命令、退出码和输出。
2. 核对自检记录与本次测试文件、NPU 尝试的对应关系。
   - 仅缺记录时先找回原始材料。
   - 尚未执行的检查交回生成器补齐。
3. 自检失败或目标仓要求尚未满足时，进入“交回修复”。
   - 由生成器修复、重新自检并运行 NPU。
   - 收到新结果后重新验收。
4. 验收完成后，沿用本轮快照中的测试和辅助文件清单、哈希，供 GPU 导出核对。辅助文件指测试使用的公共函数文件、配置或数据文件等。

#### 3. NPU 执行材料

从生成器交付的报告和原始日志核对以下内容。

1. 任务环境。
   - Python、wheel、源码和开发分支与本次交接一致。
   - 报告包含实际 Python、PyTorch 版本及已记录的源码提交，使用 torch_npu、CANN 时记录对应版本。
   - 记录实际 wheel 构建及可获得的构建、上传日期。
   - 固定版本沿用本次发行版本的源码目录和 venv。nightly 任务在上游没有新 nightly 时，已有环境满足本次 API 的测试需求即可继续验证。需要升级时交回调用方准备环境。
   - 明确要求新构建的任务，核对所用构建是否满足要求。
2. 导入路径。
   - 核对实际导入的 `torch`、`torch_npu` 的文件来源与提供的虚拟环境一致。
   - 从源码仓根目录运行时，当前目录可能遮蔽已安装的 torch_npu。出现 `torch_npu._C` 缺失时，先核对导入路径。
   - 使用指定解释器的 `-I` 模式和测试文件绝对路径，或从独立验证目录启动。
   - 测试使用公共函数等辅助文件时，提供其导入路径。保留实际框架加载位置的证据。
3. 执行范围与设备。
   - 实际运行该 API 的 `test_files`，并设置 `RUN_SUPPLEMENT_API_TESTS=1`。
   - 纯 Python、元信息等无硬件依赖的 API，按返回值、状态变化、副作用和异常行为判定。报告说明其执行不依赖 NPU 计算。
   - 确认 API 的本次全部测试均无设备依赖时，将其 `results[].api` 写入导出配置的 `device_independent_apis`。同一 API 含设备测试时保留设备核验。
   - 逐 API 核对被测调用的实际后端。用例选错设备时，修正用例后复测；用例已选 NPU 且日志确认被测算子回退 CPU 时，本次 NPU 验收记为失败。CPU 参考值的计算属于正常对照。
   - Tensor 计算场景核对实际分配、计算和同步记录，设备状态或上下文类 API 按对应行为契约核对。
   - 所需场景实际执行且断言通过才记为通过。零用例、全跳过或仅安装冒烟按实际进度记录。
4. 运行记录。
   - 保留完整命令、逐项结果、原始日志和退出码。
   - 使用 `tee`、`tail` 等日志管道时，启用 `set -o pipefail` 保留测试退出状态。
   - 缺包或导入失败时，保留具体阻塞原因。场景依赖 NPU 且 NPU 不可用时，记录该场景的阻塞。
   - 每次运行后核对实际设备、原始日志和逐项结果，退出码为 0 也要检查跳过和回退证据（如 `npu_cpu_fallback`）。要求 NPU 或 GPU 的用例如果选择了 CPU，或被测算子在运行时回退到 CPU，该场景不得计为真机通过，也不得上库。CPU 参考对照和明确标注的设备无关场景按原约定验收。
   - 发现失败、跳过、无法执行或回退时，保留受影响的用例、实际后端和原始日志，区分缺包、导入路径等环境问题与有证据的平台限制。缺包时记录缺项，交回环境准备环节补齐已知兼容依赖后用同一版用例复测，NPU 专用依赖只装在 NPU 环境。仍无法满足时保留原始结果和阻塞原因。
   - 实测证据指向平台限制时，在该 API 的 `notes` 记录设备型号、软件版本、受限调用和原始报告路径，供后续适配和复测核对。
5. 结果字段。
   - 沿用 Step0.1 登记的顶层 `execution`、`report` 和 `device_validation.npu`。
   - GPU 结果单独保存，保留有效的 NPU 结论。

#### 4. 交回修复

发现用例问题时，先记录具体问题并归档旧结果。

```bash
<本次Python> <api-adaptation安装目录>/scripts/npu_handoff.py repair \
  --source <torch_npu源码仓> --results <本次api-loop/result.json> \
  --api <results[].api> --reason <具体问题>
```

1. 保存历史。
   - 脚本将该 API 的旧结果及修复原因保存到结果目录的 `api-loop/repairs/`。
   - 原报告和日志继续保留。
2. 标记待修复项。
   - 设置 `next_step=step0.1`，将具体问题写入 `notes`。
   - NPU、GPU 当前结果重置为 `not_run`。
   - 保留原 API 身份、类别、测试文件及 `generation`。
3. 将该 API 和结果文件路径直接交给 [Step0.1](step0.1-testcase_development.md)。
   - 生成器修复后，在新尝试目录重跑 NPU。
   - Step1 收到新材料后重新验收，再上传 GPU。
   - 符合 API 契约的 NPU `fail` 或实际环境 `blocked`，按真实结果继续 GPU 参考验证。

## GPU 请求和结果

用例验收通过后进入 [Step 1.1 发送 GPU 请求](step1.1-gpu_handoff.md)。后续步骤改过用例或辅助文件时，重新验收受影响项后再走同一入口。

### 4. 等待与恢复

Step 1.1 的 `run` 命令负责直连后的等待、下载和导入。进程中断时沿用原目录重跑；在运行期间可以查看 `direct/submission.json` 和 `direct/run.json`。工作站求助已登记时，保留票据和 `awaiting_workstation_gpu` 状态，等待转发器回传。实验结果未返回前，PR 的 GPU 栏写明待验证的范围。

### 5. 验收并导入报告

1. 核对提交 SHA、`selected-files.txt`、`environment.txt`、`junit.xml`、设备审计及逐条用例结果。
   - 测试文件和辅助文件的哈希必须与本次导出一致。
   - 纯 Python API 按实际语义断言核对，报告说明其不依赖 GPU 计算。
   - 需要 GPU 的场景，核对实际 CUDA 执行及设备证据。
   - GPU 新任务由 unittest 驱动。导入后，`cuda.report` 指向原始 `execution-result.json`，草稿和发布检查共用该回执。历史 pytest 归档仍读取原 `report.json`。
2. 按逐 API 的实际结果判定。
   - 所需场景实际执行且断言通过，才记为通过。未选中、零用例或仅收集成功时保留未完成事实。
   - 环境准备失败、缺少凭据、执行端离线、缺报告或传输中断记为 `blocked`。
   - 未收齐场景或有跳过记为 `partial`，全跳过可记为 `skip`。
   - 实际断言失败或测试运行错误记为 `fail`。
   - 需要 GPU 的场景回退到 CPU 时，记录 GPU 验证未完成。
   - NPU 专属、多卡等场景不满足 GPU 服务器条件时，如实记录限制，保留用例及原断言。
3. 保存原始 artifact、日志和逐 API 报告，并按原配置导入。

```text
python <脚本目录>/step1_wsl_gpu.py import --config <导出配置> --output <唯一GPU运行目录>
```

4. 调用方协助的任务，由约定入口完成结果交回和导入。
   - 导入前核对 API 范围及源文件哈希。
   - 更新 `device_validation.cuda`，保留顶层 NPU 执行、报告、状态和路由。
   - 传输中断时继续取回原结果。用例已改变时拒绝合并旧报告，准备新一轮。

## 汇总结果并更新状态

### 1. 分析差异

1. NPU 失败、GPU 通过时，结合源码及版本差异分析 NPU 适配问题。
2. 两侧都失败时，先检查共同的用例、依赖和上游版本。
3. GPU 暴露用例错误时，按[交回修复](#4-交回修复)处理。
   - 保留两侧日志，交回错误及受影响的 API。
   - 收到修复后的 NPU 结果并重新验收后，仅为受影响的 API 发起 GPU 验证。

### 2. 同步本批状态

日志已确认被测算子回退 CPU 时，子 agent 直接在本批 `api-loop/result.json` 的 `results[]` 中按 `api` 找到对应条目，将 `execution` 和 `device_validation.npu.execution` 一并更正为 `fail`。在该条目的 `notes` 中注明被测算子、用例和现有日志位置。

沿用本次快照、报告和原始日志，直接运行以下状态脚本。待测试或实现修复后，再对改动进行复测。

```bash
python3 <api-adaptation安装目录>/scripts/record_api_status.py \
  --adapt-information <本次任务状态文件绝对路径> \
  --database <API策略数据库绝对路径> --table "<本次策略表名>" \
  --results <本次api-loop/result.json绝对路径>
```

1. 同批还有 API 等待 GPU 时，通常在收到结果或记录实际阻塞原因后同步。
2. 子 agent 执行脚本后回读两个文件，逐 API 核对写回值：
   - 在 `api-loop/result.json` 中回读同一条目。确认回退时，`status` 应为 `待适配`；首次发现实现缺口时 `next_step` 应为 `step2`，已有 `adaptation` 的实施复测仍回退时应为 `step3`。只补测试的项通过后为 `支持 / step4`。改过实现的项通过后为 `待适配 / step3.1`，复核通过后才记为 `支持 / step4`。
   - 在本批 `adapt-information.json` 中，核对 `api-status["<数据库正名>"]` 与上述条目的 `status` 一致。正名按策略表解析，结果条目有 `database_api` 时使用该值核对。
   - `next_step=step0.1` 的待生成或待修复项保持该去向；原策略为 `待适配` 的项保留该状态和方案，其余补测项记为 `补充testcase`。
   - `pass`、`fail` 必须有实际执行报告，报告路径相对结果目录。
   - `strategy` 保留最初数据库策略。
   - PR 确认合入后，由调用方回填数据库支持结论。
3. 状态脚本因任务范围、正名或对外标记冲突而拒绝时，交回调用方核对。
   - 保留真实结果、报告和拒绝原因。
   - 数据冲突单独处理，保留实际功能测试结论。

| 有效 NPU 结论 | 本批状态 | 后续 |
|---|---|---|
| 通过 | 只补测试记为 `支持`；实施回归保持 `待适配` 直至复核通过 | 只补测试交 Step4；实施回归先交 Step3.1 |
| 失败 | `待适配` | 首次发现的实现缺口交 Step2；已有适配实现的复测失败回 Step3 |
| 用例已验收，工作站票据缺失或对应旧文件 | 保留当前补测或适配状态 | 进入 Step 1.1 登记当前版本的请求，再同步状态 |
| 未运行、跳过、阻塞或部分完成 | 保留原状态，新补测项保持 `补充testcase` | 留在 Step1，保留尚缺材料和原因 |

## 其他入口与测试范围

1. 调用方指定其他 CPU/CUDA 服务器时，使用[原 SSH 远程入口](../references/remote-validation.md)。
   - 入口为 `step1_remote.py` 或本机中转的 `step1_relay.py`。
   - 作为第二轮的替代途径，沿用本次验证范围。
2. 两轮均针对本批功能测试。
   - 内存、精度、确定性按[四类测试约定](../references/test-types.md)分别评估。
   - 未生成或未运行的项目保留实际进度，当前生成 skill 明确提供功能测试。
