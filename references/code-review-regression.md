# 核对回归证据与未覆盖原因

1. **对上最终改动。** 从本轮报告找到实际加载的构建、用例快照和执行结果。返工后如果仍引用上一轮记录，核对改过的实现、用例或依赖是否影响该结果。受影响的部分用本轮重跑结果作证。
2. **找到能检错的断言。** 从原缺陷或本次改变的行为出发，指出哪次调用的哪个返回值、状态变化或副作用会让错误实现失败。用 GPU 作参照时，沿两端用例和 helper 核对初始状态、调用次序及断言取值，详细判据沿用 [Step 1](../steps/step1-testcase_validation.md)。两端分别通过只说明各自的断言成立。
3. **复核与 diff 有关的“未覆盖原因”。** 找到被排除的场景和原理由。理由是“入口不可达”，就查入口、分支条件及支持范围。理由是“其他用例已覆盖”，就找到具体用例，看它在哪次调用上断言了什么。理由是“环境不可用”，就记录待验证范围。若实现确实能走到这条路径，现有断言又区分不了对错，交回补用例并执行。

Step 1 负责生成用例的整体验收。这里重点看实际改动是否引入了新场景，或者使先前接受的排除理由失效。
