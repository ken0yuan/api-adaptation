# 四类测试及生成能力

本流程中的四类是功能、内存、精度、确定性。生成器的“计算类、框架类、分布式类、图模式类”是 API 职责分类，与这四类测试不是同一分类体系。

## 顺序

`适配策略=补充testcase → Step0.1 生成功能用例并运行 NPU → Step1 接收并按任务范围验证 GPU → 逐项评估其余三类是否需要补充`。

Step1 汇总本批功能验证状态。其余三类单独评估。尚未运行时保持待评估，不能在生成阶段把它们记为通过或不适用。

## 评估依据

| 测试类型 | 运行功能用例后需要进一步核对的内容 |
|---|---|
| 内存（`memory`） | API 是否涉及设备内存分配、持有或释放；对应生命周期、占用或泄漏风险是否已有有效测试证据 |
| 精度（`precision`） | API 是否有需要评估的数值输出或梯度；本次支持的 dtype、参考结果及误差标准是否已有足够证据 |
| 确定性（`determinism`） | API 是否有重复执行或确定性模式下的行为要求；固定输入及相关配置时，是否已有对应验证证据 |

每类分别记录 `pending_evaluation`、`needed`、`covered` 或 `not_applicable` 及简短原因。`covered` 需要可定位的已有用例和有效执行证据；数值容差、内存标准或确定性契约尚不明确时先保留待评估，不自行编造判定阈值。

## 当前生成 skill 的边界

`gen-torch-npu-api-ut` 当前定位为功能 UT 生成，支持按计算、框架、分布式、图模式四类 API 组织功能场景。

- CPU/NPU 的 `assert_close` 对照属于现有功能用例中的数值校验，不能单凭这一条宣称精度专项已覆盖。
- 同步场景使用固定已知值不等于已验证重复执行的确定性。
- 现有规范未提供独立的内存、精度、确定性用例生成模式，也没有运行后自动评估三类补测需求的流程。

api-adaptation 负责顺序编排及逐类需求记录；生成 skill 仍由其维护者独立演进。其余三类的生成能力接入前，交回补测需求，不把未知能力当作已实现。
