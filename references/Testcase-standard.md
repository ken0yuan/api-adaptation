# 覆盖情况与执行结果

当前入口结合本次adapt-information中的API状态和数据库策略分流：补充testcase进入Step0.1；待适配交Step2后直接结束；支持项结束该API并交回主agent。Step1使用已有环境执行测试，再更新本批状态。

覆盖完整性和执行是否通过是两个独立判断。覆盖判定针对本次 API 的功能测试要求，不宣称穷尽所有输入或证明全面支持。

本页的覆盖及执行结果对应先行的功能测试；功能运行后再按[四类测试约定](test-types.md)评估内存、精度、确定性补测需求，不将功能通过等同于四类均通过。

| 覆盖情况 | 执行结果 | 动作 |
|---|---|---|
| 无用例 | 未执行 | 生成用例，再执行 |
| 部分覆盖 | 任意 | 补明确缺失场景，再执行；已有失败证据保留 |
| 完整覆盖 | 未执行或旧结果已不适用 | 在本次源码和环境执行 |
| 完整覆盖 | 通过 | 交回本次功能验证结果 |
| 完整覆盖 | 失败 | 分析用例、环境及实现原因，按需适配 |
| 尚未判断 | 任意 | 补充覆盖依据，不直接认定完整 |

只处理本批明确的补测要求，已有文件和有效记录继续复用，不要求建立全仓映射。Step0.1生成后执行状态保持not_run，由Step1实际执行；不从策略名称推断覆盖完整。

生成后的覆盖检查应能把本次需要验证的契约、参数和边界对应到具体测试及有效断言。测试方法名、数量、注释表格或文件存在不能单独证明完整；明确缺口记为 `partial`，尚无法判断记为 `unknown`。

只有本次指定 NPU 环境中所需场景实际执行并全部通过，才记 `execution=pass`。全跳过记 `skip`，环境使测试无法启动记 `blocked`，部分通过但仍有跳过或未执行场景记 `partial`，实际断言失败或运行错误记 `fail`。完整功能验证需要覆盖依据和执行通过同时成立。
